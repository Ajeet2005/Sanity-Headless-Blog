01 अनुभव — The Name & Its Meaning

Fig 1 — अनुभव: The Nepali/Sanskrit word for "Experience"

Meaning in Nepali & Historical Roots

अनुभव (Anubhav) is a Nepali and Sanskrit word that directly translates to "experience". It derives from two Sanskrit roots:

  • अनु (anu) — "along, following, after"
  • भव (bhav) — "becoming, existence, feeling"

Together, anubhav means "that which follows from living" — the perception, wisdom, and understanding that a person gains through direct experience of the world.

In Nepali culture and literature, अनुभव carries a weight far beyond casual meaning. It refers to first-hand, lived knowledge — not something read in textbooks, but something felt, endured, and ultimately understood through one's own journey. The great Nepali poets and thinkers have long valued अनुभव as the most authentic form of wisdom — the kind that only comes from walking the path yourself.

📜 Historical Note In classical Sanskrit philosophy, anubhava (अनुभव) is one of the pramāṇas — valid means of knowledge. It refers specifically to pratyakṣa (direct perception), making it the most intimate and undeniable form of knowing. This philosophical depth is exactly what this project captures.

Why We Named It Anubhav

This blog is not just a technical platform — it is a personal documentation of experiences. Every article, every journal entry, every piece of content published here represents something lived and learned.

The name aligns with the project's identity in three key ways:

  • Lived (जिइएको) — The content comes from real experiences, not hypothetical ideas. Each post documents something the author has personally encountered.
  • Learned (सिकेको) — Knowledge is distilled from those experiences. Technical tutorials, personal reflections, and insights all originate from genuine learning.
  • Documented (लेखिएको) — Anubhav gives those experiences a permanent home. The blog preserves them so others can learn from them too.

The tagline, "Lived, Learned, Documented", captures this perfectly. Anubhav is not a random brand name — it is a Nepali word that describes exactly what this platform does: it turns lived experiences into shared knowledge.

02 What Is Anubhav?

Anubhav is a modern, full-featured headless blog platform built for personal blogging, journal writing, and premium content publishing. It combines a powerful content management backend with a lightweight, fast frontend to deliver a reading experience that feels native and premium.

Fig 2 — High-level architecture: Sanity CMS → Express API → Static Frontend

Anubhav is a three-layer system:

LayerTechnologyRole
Content SourceSanity Studio (Headless CMS)Write, organize, and publish all content
API ServerExpress.js + MongoDBHandle payments, reviews, push notifications, and auth
FrontendStatic HTML/CSS/JS (PWA)Render content, search, filter, and display posts

What You Can Expect to See in Anubhav

  1. A clean, minimal blog feed with categorized and tagged posts
  2. A personal Journal section for reflective entries
  3. Premium posts gated behind Khalti payments (Nepal's payment gateway)
  4. Private posts accessible only to authenticated users
  5. Push notifications — get notified the moment a new post drops
  6. Dark & Light mode with persistent preference
  7. Real-time search across titles, excerpts, tags, and categories
  8. Reviews & Feedback system per post with version history
  9. Installable as an app (PWA) — works offline too
  10. Rich link previews when shared on social media (dynamic OG tags)

05 Frontend Architecture

The frontend is deliberately framework-free. It uses plain HTML files, vanilla CSS, and native JavaScript. This is a conscious architectural choice — no React, no Vue, no build step. The result is a zero-dependency, instantly-loading frontend that anyone can understand and modify.

HTML5 CSS3 Custom Properties Vanilla JavaScript (ES Modules) Service Worker (PWA)

Static HTML & Vanilla JavaScript

The frontend consists of four standalone HTML pages:

PagePurpose
index.htmlBlog home — lists all blog and premium posts with search, categories, and tags
journal.htmlJournal section — displays personal journal-type entries
post.htmlSingle post view — fetches content by slug query parameter from Sanity
login.htmlFirebase email/password authentication portal

Each page is self-contained — it includes its own styles and scripts inline. The JavaScript fetches content directly from Sanity's public CDN API at runtime, so the HTML files themselves are static and can be served from any CDN or static host.

Content Fetching — GROQ Queries

Sanity uses a query language called GROQ (Graph-Relational Object Queries). Instead of REST endpoints with fixed responses, GROQ lets the frontend ask for exactly the data it needs — similar to GraphQL, but purpose-built for document-based content.

💡 What is GROQ? GROQ is Sanity's open-source query language. It lets you filter, project, and join documents in a single query — without needing a backend to transform the data. Think of it as SQL for JSON documents.

For example, the homepage fetches all blog and premium posts with this GROQ query:

*[_type == "post" && (!defined(postType) || postType in ["blog", "premium"])] {
  _id, title, slug, publishedAt, excerpt, readingTime,
  isPrivate, isPremium, postType,
  "authorName": author->name,
  "authorImage": author->image.asset->url,
  "imageUrl": mainImage.asset->url,
  "categories": categories[]->title,
  tags
} | order(_createdAt desc)

This single query fetches posts, resolves author references, extracts image URLs, and sorts by date — all in one HTTP request to Sanity's CDN. No backend processing required.

Theming — Dark & Light Mode

The entire theme system is built with CSS Custom Properties (CSS variables). A single data-theme attribute on the <html> element switches every color in the interface. 

/* Light theme (default) */
:root {
  --bg: #f9f9f9;
  --surface: #ffffff;
  --text: #1a1a1a;
}

/* Dark theme */
[data-theme="dark"] {
  --bg: #0f0f0f;
  --surface: #1a1a1a;
  --text: #e8e8e8;
}

The user's preference is saved in localStorage under the key "theme", so it persists across sessions without any backend involvement.

Progressive Web App (PWA)

🔧 What is a PWA? A Progressive Web App is a website that behaves like a native app. It can be installed on the home screen, works offline through a Service Worker, and receives push notifications — all without an app store.

Anubhav is a fully installable PWA. The three components that enable this:

  1. manifest.json — Declares the app's name, icons, theme color, and display mode (standalone)
  2. firebase-messaging-sw.js — The unified Service Worker that handles both offline caching and FCM push notifications
  3. HTTPS — Required by browsers for Service Worker registration

The Service Worker uses a "network-first" caching strategy: it tries to fetch from the network, and if that fails (offline), it serves the cached version. This ensures users always see the latest content when online, but can still browse previously loaded pages when offline.

Firebase Authentication

Private posts require authentication via Firebase Auth (email/password sign-in). The Firebase SDK is self-hosted in the vendor/ folder rather than loaded from Google's CDN (gstatic.com), because privacy browsers like Brave and Edge block third-party tracking domains — which would silently break login.

When a user clicks a private post card, an inline authentication modal appears. Upon successful sign-in, the Firebase ID token is stored in localStorage with a 1-hour expiry. This token is also sent as a Bearer header when subscribing to push notifications, so the server can link the device to the user.

Push Notifications — Bell UI

The notification bell (🔔) in the header opens a popup with a single "Enable Notifications" button. No login is required — any visitor can subscribe their device. The flow:

  1. User clicks the bell → popup appears (no browser permission prompt yet)
  2. User clicks "Enable Notifications" → browser requests permission
  3. On grant → FCM registers this browser and returns a device token
  4. The token is sent to the Express server (POST /api/notifications/subscribe)
  5. Server stores the token in MongoDB

The system also handles edge cases: iOS requires the site to be installed as a PWA (iOS 16.4+), Firefox is not supported by FCM web push, and in-app browsers (Instagram, WhatsApp) are detected and the user is guided to open in a real browser.

SEO — Dynamic Open Graph Meta Tags

When a post link is shared on social media, the Express server intercepts the request to post.html, fetches the post's title, excerpt, and image from Sanity, and dynamically injects the correct Open Graph meta tags before serving the HTML. This is known as server-side rendering for crawlers.

Regular users get the same static post.html with client-side rendering, but social media crawlers (Facebook, Twitter, LinkedIn) see fully populated meta tags — giving rich link previews with the post's title, description, and cover image.

06 Backend Architecture (Express + MongoDB)

The backend is a single Express.js server (server.js) that handles everything the static frontend cannot: payment processing, review storage, push notification broadcasting, and dynamic meta tag injection. It connects to MongoDB (via Mongoose ODM) for data persistence.

Express.js v4 MongoDB + Mongoose Firebase Admin SDK v14 Node.js Crypto (HMAC)

The server also serves the static frontend files, so a single deployment hosts both the API and the website.

Khalti Payment Integration

Fig 3 — Premium subscription payment flow via Khalti

Khalti is Nepal's popular digital payment gateway. Anubhav uses it to monetize premium posts. The integration follows a standard redirect-based payment flow:

  1. Initiate — Frontend sends POST /api/payment/initiate with the user's email and amount
  2. Redirect — Server creates a Khalti payment session and returns a payment_url
  3. Pay — User is redirected to Khalti's checkout page to complete payment
  4. Callback — Khalti redirects back to GET /api/payment/callback?pidx=…
  5. Verify — Server calls Khalti's lookup API to confirm the payment is genuine
  6. Activate — On success, the subscription is marked active in MongoDB
🔒 Security The Khalti secret key stays on the server. Payment verification uses Khalti's server-to-server lookup API — the client never handles payment confirmation directly.

Review & Feedback System

Each post can receive star ratings (1–5) and text feedback. Reviews are identified by name + slug combination. When a review is updated, the old version is archived in a ReviewHistory collection with a version number — this is a simple implementation of event sourcing, preserving an audit trail of every change.

Push Notification Engine (Firebase Cloud Messaging)

Fig 4 — End-to-end push notification flow from publish to browser alert

When a new post is published in Sanity, the entire notification chain fires automatically:

  1. Sanity fires a webhook (HTTP POST) to the Express server
  2. Server verifies the webhook's HMAC-SHA256 signature
  3. Server queries MongoDB for all active FCM device tokens
  4. Server sends a push message to each device via Firebase Admin SDK
  5. Browser's Service Worker receives the message and shows a native notification
  6. Clicking the notification opens post.html?slug=… for that post

Draft saves are filtered out server-side (documents with IDs starting with drafts.) so subscribers are only notified when a post is actually published.

Webhook Signature Verification

💡 What is HMAC-SHA256? HMAC (Hash-based Message Authentication Code) is a way to verify both the integrity and authenticity of a message. The sender and receiver share a secret key. The sender hashes the message with the key and attaches the hash. The receiver re-computes the hash and compares — if they match, the message is genuine and untampered.

Sanity signs every webhook request with sanity-webhook-signature: t=<timestamp>,v1=<hmac>. The server:

  1. Extracts the timestamp and signature from the header
  2. Rejects stale signatures (5-minute window for replay protection)
  3. Recomputes HMAC-SHA256(secret, timestamp + "." + rawBody)
  4. Compares using crypto.timingSafeEqual() to prevent timing attacks

This ensures that only Sanity — with the matching SANITY_WEBHOOK_SECRET — can trigger notifications. A malicious party cannot forge a valid webhook request without the secret.

07 Sanity Backend (CMS)

What Is a Headless CMS?

Fig 5 — Traditional CMS vs Headless CMS architecture

A traditional CMS (like WordPress) bundles the content management, the database, and the frontend together into one monolithic system. Change one, and everything must be redeployed.

A headless CMS separates content management from content presentation. The CMS only manages content and exposes it through an API. The frontend is completely independent — it can be a website, a mobile app, or even an IoT device. This separation is called decoupled architecture.

Sanity is the headless CMS Anubhav uses. It provides:

  • A cloud-hosted document store for all content
  • A customizable authoring interface (Sanity Studio)
  • A real-time API with GROQ query language
  • Webhooks to trigger actions when content changes
  • An image CDN with on-the-fly transformations

Author Schema

Stores author name, slug, profile image, and a short bio. Posts reference authors through Sanity's document reference system.

Category Schema

Simple taxonomy with title and description. Posts can belong to multiple categories.

Block Content Schema

Defines the rich text editor capabilities. Beyond standard text formatting (bold, italic, headings, quotes, links), it supports:

  • Inline images with optional captions
  • Code blocks with language selection (HTML, CSS, JS, Python, etc.) and optional filename

Sanity Studio

Sanity Studio is a React-based web application that runs locally (or is deployed) and provides the authoring interface. It connects to the same Sanity project as the frontend, so any content published in the Studio is immediately available through the API.

The Studio configuration is minimal:

// sanity.config.js
export default defineConfig({
  name: 'default',
  title: 'My-Blog',
  projectId: 'xsd8o1za',
  dataset: 'production',
  plugins: [structureTool(), visionTool()],
  schema: { types: schemaTypes },
})

Two plugins are used: structureTool (the document editing UI) and visionTool (a GROQ query playground for testing queries directly in the Studio).
